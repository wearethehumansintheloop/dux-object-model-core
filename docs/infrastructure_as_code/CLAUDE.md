## DUX Research Platform Overview

The DUX Research Platform is a Neo4j-based research data processing and analysis system that forms part of the larger Declarative UX (DUX) ecosystem. It provides AI-powered chat interfaces, data loading capabilities, and API services for managing UX research objects.

## Architecture

### Core Services
- **Neo4j Database** (port 7474/7687): Graph database storing DUX research objects
- **API Service** (port 8504): FastAPI backend with LLM integration and insight chains
- **Bot Service** (port 8501): Streamlit-based research chat interface
- **Loader Service** (port 8502): Data ingestion and embedding generation
- **CSV Bot** (port 8506): CSV data processing interface
- **White Label UI** (port 3000): Next.js frontend connecting to API

### DUX Object Model Integration
The platform works with DUX v9.6 schema objects including:
- **Core Objects**: Session, Data, Frame (research platform specific)
- **Junction Objects**: Evidence Junction, Insight Junction, Provenance Junction
- **Collection Objects**: Study, Report, Report Gallery
- **Ecosystem Objects**: Problem, Behavior, Result, Insight (from dux-object-model-core)

## Key Integration Points

### With DUX Object Model Core
- Validates objects against v9.6 schemas located in `../dux-object-model-core/src/dux_v9.6_split_schema/`
- Processes research objects through validation pipeline
- Stores validated objects in Neo4j graph database

### With Duckie CLI
- Ingests objects generated by Duckie's BDD scenario processing
- Provides graph-based querying of research scenarios and test results

### With White Label UI
- Serves insight chain data via `/api/insight-chains` endpoint
- Provides real-time LLM responses through streaming endpoints

## Data Flow

1. **Data Ingestion**: Raw research data loaded through Loader service
2. **Object Validation**: Multi-layer validation (schema, quality, integrity)
3. **Graph Storage**: Validated objects stored in Neo4j with relationships
4. **Vector Embeddings**: Generated for semantic search and RAG operations
5. **API Access**: Objects accessible via FastAPI endpoints for frontend/external use

## DUX Development Principles

### Core DUX Method
- **Natural Language First**: All DUX objects start as markdown files in human-readable format
- **Evidence-Driven**: Every claim must be traceable to concrete evidence via Provenance objects  
- **Atomic & Testable**: Each object serves a single purpose and can be validated independently
- **Schema Compliance**: All objects must validate against their JSON schema definitions

### Slow Bullet Mode (Required)
**Take one atomic unit of work at a time. Don't jump steps or assume context.**

Core principles:
- **One atomic unit per interaction** - Focus on a single Problem, Behavior, or Result
- **Confirm alignment before continuing** - Get explicit confirmation before proceeding
- **Show structure before content** - Present outlines before generating full implementations
- **Ask clarifying questions first** - Understand intent before producing output

### Quality Standards
- **Traceability**: Every claim must link to evidence via provenance_id
- **Atomicity**: Each object serves one clear purpose
- **Testability**: All behaviors and results must have measurable acceptance criteria
- **Type Safety**: Use type hints and validation for all DUX objects
- **Error Handling**: Graceful degradation and meaningful error messages

## Common Development Patterns

### Adding New Object Types
1. Define schema in `../dux-object-model-core/src/dux_v9.6_split_schema/`
2. Add validation steps in `features/steps/`
3. Update API endpoints in `apps/api/main.py`
4. Add BDD scenarios in `features/`
5. Ensure schema validation passes before implementation

### API Development
- **API-First**: Design APIs before implementation
- **RESTful**: Standard HTTP methods for CRUD operations
- **Streaming**: Real-time processing for LLM responses
- **Validation**: Input validation at API boundaries
- **Error Responses**: Consistent error format with actionable messages

### Debugging Neo4j Queries
- Access Neo4j browser at `http://localhost:7474`
- Use Cypher queries to inspect graph structure
- Check validation results in `validation_pipeline/`
- Optimize queries for common access patterns

### Working with LLM Chains
- LLM configurations in `core/chains.py`
- Streaming responses handled via `QueueCallback` pattern
- RAG chains combine Neo4j retrieval with LLM generation
- **Prompt Engineering**: Structured prompts for consistent object extraction
- **Error Recovery**: Handle LLM failures gracefully

## Testing Strategy

The platform uses BDD testing with comprehensive validation:
- **Schema Validation**: JSON Schema compliance for all objects
- **Quality Validation**: Data completeness and consistency checks
- **Integrity Validation**: Cross-object relationship verification
- **Workflow Validation**: End-to-end research process validation
- **Unit Tests**: Test individual object validation and processing
- **Integration Tests**: Test API endpoints and database operations
- **End-to-End Tests**: Test complete workflows from upload to storage

Run tests frequently during development to ensure object integrity and system reliability.
